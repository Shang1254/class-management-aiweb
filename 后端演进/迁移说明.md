# 后端演进方案（论文「系统扩展与部署」章节素材）

当前系统为**纯前端 + localStorage**（双击即用、零部署），适合单机演示与轻量班级使用。
若要在全校范围实际部署（多用户并发、数据集中、移动端互通），按下表迁移到中心化后端即可——
**前端 14 个页面一行不用改**：`store.js` 是全项目唯一数据出入口，只需把它的 13 个方法换成 HTTP 调用。

## 一、云服务选型评估（免费额度为 2026 年公开信息，以各家官网为准）

| 能力 | 推荐 | 免费额度 | 本项目评估 |
| --- | --- | --- | --- |
| 数据库 + 认证 + 存储 | **Supabase** | 500MB 库 / 1GB 存储 / 5 万 MAU | ✅ 首选。Postgres 建表脚本已备好（`supabase_schema.sql`），自带 Auth 可接管登录（SHA-256 前端摘要升级为服务端 bcrypt + JWT），RLS 行级安全正好补齐"权限只在客户端过滤"的短板 |
| 国内低代码后端 | YesApi 果创云 | 500+ API、每日免费额度 | ⚠️ 备选。Supabase 在国内访问速度一般时的替代，零代码建表建接口，但自建 SQL 受限 |
| 手机消息推送 | **ntfy.sh** | 无限制（公开通道） | ✅ **已接入**：通知发布时可一键推送到学生手机（App/网页订阅 topic），浏览器直发、免密钥 |
| 微信推送 | WXPush | 10 万次/天 | 🔧 需公众号 + 服务端持密钥，纯前端不可行；有后端后可接入（家长通知场景有价值） |
| 邮件发送 | Resend / Mailtrap | 3000~4000 封/月 | 🔧 需服务端（API Key 不能放前端）。接入 Supabase Auth 后自带找回密码邮件，无需另接 |
| 短信验证码 | 阿里云短信 | 预置模板免资质 | 🔧 需服务端 + 资质。班级系统用学校统一身份认证即可，短信非必需 |
| 文件存储 | Cloudflare R2 | 10GB / 10 万次调用/天 | 🔧 需服务端签名。用于班级共享资料/学生头像；有后端后接入 |
| 日历集成 | Google Calendar API | 100 万次/天 | ⚠️ 需 OAuth + 后端，且国内访问受限；**课表导出 .ics 已原生实现**（手机日历直接导入），覆盖 90% 场景 |
| 中国日历/节假日 | cn-calendar-skill | 零 API | ✅ **已原生实现**（`js/cn-calendar.js`）：农历/节气/调休/工作日计算 |
| 学生身份核验 | SheerID / 微信实名 | — | ❌ 不适用：学校统一身份认证（正方 CAS）已解决真实身份，无需第三方 |

## 二、迁移路径（三步走）

### 第 1 步：建库建表（已完成脚本）
在 Supabase SQL Editor 执行 `supabase_schema.sql`：18 张表与当前 localStorage 实体一一对应，
`uuid[]` 承载教师任教班级/签到名单/竞赛获奖学生等数组字段，`unique` 约束承载幂等 upsert 语义
（如同一学生同一天考勤唯一、同一测验只能作答一次）。

### 第 2 步：替换 store.js 数据层
| 现有方法 | 后端对应 |
| --- | --- |
| `Store.list(entity)` | `supabase.from(table).select()`（按角色加 RLS/filter） |
| `Store.add(entity, item)` | `insert()` |
| `Store.update(entity, id, patch)` | `update().eq('id', id)` |
| `Store.remove(entity, ids)` | `delete().in('id', ids)` |
| `Store._log(...)` | `insert` 到 `op_logs`（或由数据库触发器自动审计） |
| 审计/迁移/学期工具 | 保留在前端，纯计算逻辑与存储无关 |

页面层无感知：所有页面只调 `Store.*`，不碰 localStorage（已有架构铁律保证）。

### 第 3 步：认证与安全升级
1. 登录迁移到 Supabase Auth（或保留自研 JWT 接口），密码改服务端 bcrypt；
2. 启用 RLS：学生仅见本人数据、教师限任教班级、管理员全量——把"前端过滤"变成"数据库强制"；
3. 后端 + 定时任务可把 ntfy 推送升级为按角色精准推送（家长/学生分组）。

## 三、预期成本与部署

- **免费额度足够**：6 个班 75 人的规模，Supabase 免费层余量充足（成绩 ~2500 行/学期，全库 <10MB）；
- **部署形态**：前端静态文件（校园网服务器 / Vercel / 对象存储）+ Supabase 后端，HTTPS 域名访问；
- **合规**：学生手机号/住址等个人信息入库后，需遵循最小权限原则（家长电话仅辅导员可见）并保留审计日志（`op_logs` 已设计）。

> 说明：本方案对应论文「系统设计—扩展性设计」与「总结与展望」章节；
> 迁移不改动前端代码的结论来自架构设计（数据访问层隔离），是可验证的工程事实。
