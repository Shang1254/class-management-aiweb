# 支付宝缴费接入方案（缴费中心微应用）

> 本文是《与学校现有系统集成方案》的姊妹篇：缴费功能按同样的「预留缝 + 可离线验证」哲学落地。
> 结论先行：**接入缝已经全部预留好——拿到签约应用与网关后，改动量是「填一份配置 + 起一个签名服务」量级，不改任何业务代码。**

## 一、现状（已做 / 已预留）

班级缴费中心是**独立微应用**（`缴费中心/`，自带存储与 UI，经契约桥挂接宿主），已完成：

| 能力 | 状态 | 说明 |
| --- | --- | --- |
| 费项发布 / 应缴名单 / 催缴 / 核销 / 账本 / 公示 | ✅ 已做 | 金额以「分」存储；核销自动入账；公示带人民币大写 |
| 内置演示收银台 | ✅ 已做 | 浏览器闭环演示（演示二维码水印，无资金流动），答辩零配置 |
| 本机签名服务 `pay_server.py` | ✅ 已做 | 真实 HTTP 链路：下单 → 轮询 → **主动查单** → 异步通知 → **服务端验签** → 按日对账；零依赖标准库 |
| 支付宝沙箱真实签名 | ✅ 预留缝 | `config.json` 填沙箱 appId + 商户私钥（`pip install pycryptodome`）→ 自动切 RSA2 真实签名，调用「订单码支付」`alipay.trade.precreate` 出真二维码 |
| 主动查单 `alipay.trade.query` | ✅ 已实现 | 官方安全红线「支付结果以异步通知或查询接口为准」：本地收不到异步通知（官方亦说明沙箱无法测试异步通知），轮询时主动向支付宝查单，`TRADE_SUCCESS` 即幂等入账 |
| 校园支付网关空预设 | ✅ 预留缝 | `PAY.GATEWAYS` 第三条空预设，填网关地址 + appId 即启用 |

## 二、落地形态与技术要点

```
学生浏览器                      网关服务（三选一）                     支付宝
────────────                  ─────────────────                   ──────
缴费中心收银台 ──下单──▶  mock：浏览器内闭环（演示）
      │                    local：pay_server.py 签名 ────RSA2────▶ 沙箱/正式 precreate（订单码支付）
      │                    campus：学校支付网关  ────签约通道────▶ 商户应用
      │◀──二维码/收银台链接──┘
      └──2s 轮询查单──▶  query：本地状态；沙箱模式自动向支付宝
      │                  alipay.trade.query 主动查单 → 命中即幂等入账
      │
支付宝服务器 ──────异步 notify────▶  先验签（支付宝公钥 RSA2）→ 幂等入账 → 返回 success
管理员对账 ───────按日 reconcile──▶  与缴费单核销闭环
```

要点（与支付宝官方 Skill「安全红线」逐条对齐）：
1. **订单幂等**：缴费单号（`out_trade_no`）全局唯一，重复下单/重复通知不重复入账（已在 pay_server 与前端双重实现）。
2. **验签在服务端**：回执签名（HMAC 演示 / 支付宝公钥 RSA2 正式）只在网关侧校验；浏览器只展示「已验签」徽章——与宿主 `Auth.loginAsExternal` 的 `trusted` 语义同源。
3. **支付结果口径**：前台支付结果不可信，以「异步通知」+「主动查单」双通道为准；未确认支付结果前不要求用户重复付款。
4. **金额分存储**：杜绝浮点误差；公示环节输出人民币大写（壹贰叁…）。
5. **密钥边界**：商户私钥只存服务端 `config.json`（或校园网关），不进日志、不进前端、不进公共仓库；时间戳用 `yyyy-MM-dd HH:mm:ss`（官方要求，非 ISO 格式）。

## 三、需要学校 / 班级提供什么

| 主体 | 提供物 | 用途 |
| --- | --- | --- |
| 学校（推荐） | 统一支付网关（财务处/网络信息中心建设的校园缴费平台）对外开放地址 + 授权 | `campus` 预设；资金走学校对公账户，最合规 |
| 学校 | 校园统一认证网关验签后端 | 让契约桥的 `trusted` 由服务端置位（已预留 CAS 缝） |
| 班级（自行试点） | 支付宝开放平台签约应用（企业/个体户主体，「当面付」或「手机网站支付」产品） | `local`→`campus` 过渡方案；个人主体可先用**沙箱**完成全流程验证 |
| 无 | —— | 以上都没有时，演示收银台 + 收款码登记模式照常可用（未配置 ≠ 坏了） |

## 四、到账后改动量

| 场景 | 改动 |
| --- | --- |
| 用支付宝沙箱验证 | `缴费中心/config.json.example` 重命名为 `config.json`，填 appId + 私钥；`pip install pycryptodome`；重启服务。前端零改动 |
| 学校网关就绪 | 缴费中心「设置 → 支付网关」选校园网关，填 base + appId。前端零代码改动（预设已留） |
| 统一认证单点登录 | 宿主侧按《与学校现有系统集成方案》启用 `Auth.loginAsExternal`；缴费中心自动继承宿主会话，零改动 |
| 异步通知公网可达 | 校园网关反向代理到 `pay_server` 的 `/api/pay/notify`；或由学校网关自行承担 |

## 五、答辩口径（三句话）

1. 「缴费中心是独立微应用，宿主只加了一个菜单入口和一个桥接页——身份与名册按契约自动接入，这正是我们三条集成缝设计哲学的第四条落地。」
2. 「演示收银台闭环不需要任何配置；本机签名服务演示了真实支付链路的全部关键环节——签名下单、异步通知、服务端验签、幂等入账、按日对账，拿到沙箱密钥即可真实签名。」
3. 「真实扣款涉及资金主体资质，必须由学校财务统一签约——我们把缝留好了，改动量是填一份配置，不是改代码。」

## 六、边界（不做什么）

- 不做资金代管与清结算：班费团费的资金主体是班级，系统只做**登记、对账与公示**；
- 不做分期 / 借贷 / 多币种 / 发票；
- 演示二维码不可真实扫码付款（带「演示」水印，诚实标注）；
- 不采集学生联系方式，催缴名单仅经办人可见；
- 已核销订单的退款需先在账本做冲销，不做自动冲账。
